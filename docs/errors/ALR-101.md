# ALR-101: The mail server refused the sign-in

alertd connected to the mail server of `[email]` in `alerts.toml`, over TLS, and signed in with its `user` and `password`, and the server said no: "the server refused the password", with the server's own reply, such as `535 5.7.8 authentication failed`, or "the server could not sign in". Nothing was sent, and the message waits in the outbox, which alertd tries again after 1, 5, 15 and 30 minutes and then every hour, for 24 hours. Until the account or the settings change, each try ends the same way.

## What to do

1. Check the user and the password with the provider. The user is often the whole address. Many providers do not take an account's own password for a program, and want an app password made for this use; some want two-step sign-in turned on before they make one.
2. Change them on the Alerts page, under Email, and choose **Save**, or edit `/system/settings/alerts.toml` and run `elevate service alertd reload`. The file holds the password: it must be root's alone (`chmod 600`), as alerts.toml(5) says.
3. Check the server and the port: a provider's submission server is on port 587 (STARTTLS) or 465 (TLS from the start).
4. To check that it worked, choose **Send a test alert**, or run `elevate alerts test`: the line for email says that it was sent.
