# SEC-140: The clock was not set by a time server

`timed` has not set the clock from a time server in the last day, or has never. It asks over Network Time Security as soon as the network is up, and again every few minutes while it is wrong, so a computer that was on for hours and has not set it has a problem. The clock matters beyond the time shown: TLS certificates are valid between two dates, so with a wrong clock the update server, a web site or a mail server is refused; the log's times, and a backup's, are wrong; and a snapshot is named for the day it is made.

## What to do

1. Run `timedatectl timesync-status`. It says which servers timed tried and what each answered.
2. If no server answers, the network is the cause: run `netcheck`, which finds the layer where it stops working. A firewall in front of this computer must let UDP port 123 and TCP port 4460 out.
3. If your network blocks both, name a time server it allows in `/system/settings/timed`; `timed(5)` lists the settings.
4. Run `service timed explain` if the service is not running, and start it with `elevate service timed start`.
5. To check that it worked, run `timedatectl timesync-status`, which says `Synchronized: yes`, then `elevate dukovo-check`: the line for `clock` passes.
