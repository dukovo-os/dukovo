# ALR-102: The mail server offers no TLS

On port 587, alertd connects and asks the server to start TLS (STARTTLS, RFC 3207) before it sends the password or the message. This server's answer to EHLO does not list STARTTLS, so alertd stopped: it never sends mail, or a password, in the clear, and no setting turns that off. The line names what the server offers. Nothing was sent. The message waits in the outbox and is tried again, with the same result until the server or the setting changes.

## What to do

1. Check `server` and `port` in the `[email]` table of `/system/settings/alerts.toml`, or in the Alerts page's Email card. It must be the provider's submission server, not the server that mail is delivered to, and the provider's own page names its port: 587 with STARTTLS, or 465 with TLS from the first byte.
2. If the provider says 465, set `port = 465`: TLS is then on from the first byte and nothing is asked.
3. If the server really has no TLS, it cannot be used. Use a provider that has, or a webhook, such as ntfy, which also reaches a phone.
4. Run `elevate service alertd reload` after editing the file, then `elevate alerts test`: the line for email says that it was sent.
