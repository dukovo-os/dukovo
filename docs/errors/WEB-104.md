# WEB-104: The website did not answer after the change, so the change was taken back

After the new site is live and nginx has read it, `website` asks for a file of random name, put in the site's folder, over 127.0.0.1 under each of the site's names, for up to 10 seconds each. An HTTPS site is asked over TLS, with the certificate's chain and the name checked, and its port 80 must answer with a redirect to the HTTPS address. A PHP site also asks for a small PHP file, which proves that PHP-FPM answers. One of them did not answer as it should, and the line says which: "The site did not answer: port 80 for www.shop.example.org answered 404 from another server".

`website` then took every step back: the site's file, nginx's service file and the restart it made, the site's folder when it made it, and nginx and PHP-FPM turned off again when it turned them on. Nothing of the change stays.

## What to do

1. Read the line: it names the port, the name and what answered. A 404 or another site's page says that another server of nginx answers to that name first: `website list` and the `server_name` lines of `nginx.conf` show which.
2. For HTTPS, a certificate that does not cover the name, or one that has expired, fails the check: `cert list` shows each certificate's names and its end.
3. For a PHP site, `service php-fpm explain` says why PHP-FPM is not answering.
4. `service nginx explain` says why nginx is not running, if that is the cause, and `log -s nginx` has its own lines.
5. To check that it worked, run the command that stopped again: it ends with the address of the site, and `website list` lists it.
