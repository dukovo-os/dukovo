# SEC-180: The processor's microcode cannot close a flaw

`dukovo-check` read the kernel's files in `/kernel/devices/system/cpu/vulnerabilities`, one for each speculative-execution flaw a processor can have, and at least one says `Vulnerable` for want of microcode (`No microcode`, or `no microcode` after what the kernel attempted). The kernel closes these flaws with controls that the processor's microcode provides, and the microcode this processor runs lacks them. A program that runs on this computer may then be able to read what another program, or the kernel, holds in memory. The line names each flaw as its file does, such as `srbds`.

A flaw that is open for another reason, a protection the kernel does not have yet or one turned off on its command line (dukovo-boot(7)), does not raise this warning: no microcode closes it, and the line that passes names it. Neither does one in a virtual machine, which runs its host's microcode: the host's administrator updates that.

## What to do

1. Run `lscpu`. Its last lines, `Vulnerability` and the flaw's name, say what the kernel found for each, and the file with the flaw's name in `/kernel/devices/system/cpu/vulnerabilities` has the same line.
2. Install a newer firmware set with `elevate update apply`, which carries the microcode that Intel and AMD give out, and restart. The microcode is loaded early in each start.
3. If the line is still there, the firmware set has no newer microcode for this processor: look for a BIOS update from the machine's maker, which carries newer microcode, and install it as the maker says.
4. A flaw that no update closes stays open for as long as the processor is used. Run only programs and virtual machines you trust on it, and ask the maker whether the processor is still supported.
5. To check that it worked, run `elevate dukovo-check`: the line for `processor flaws` passes.
