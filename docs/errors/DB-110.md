# DB-110: The copy was not put into the database

`database restore` made the new database and ran the bundle's `pg_restore` to put the copy into it, and `pg_restore` ended with an error. The first of what it said is in the lines before the ID, up to 16 KiB of it, and its last line says how `database` took back what it had made: the new database is removed again, and with `--over` the database that was kept under another name has its name back. When taking something back failed too, the line says which database stays and why, so that nothing that held data is lost: the old database is never removed.

The reasons are usually in `pg_restore`'s words. A copy that creates an extension PostgreSQL does not trust the database's owner with fails, because the restore is made as the owner of the database; a copy from another computer may grant privileges to a role that is not here; the disk may be full. The first time `database restore` runs, Dukovo also asks whether the bundle may run with root's access, and a restore that nobody answers fails here.

## What to do

1. Read what `pg_restore` said and fix what it names: make the role it grants to with `elevate createuser -U postgres NAME`, or free space on the disk (`elevate df -h`).
2. If it says the bundle may not run with your access, run `elevate pg_restore --version` at a terminal once and answer `A`, then restore again.
3. Run `database restore` again. A new database made by the failed try is already removed; `elevate database list` shows what there is.
4. To restore a copy that needs an extension, make the database with `elevate createdb -U postgres NAME_new`, add the extension with `elevate psql -U postgres -d NAME_new -c 'CREATE EXTENSION name'`, and put the copy in with `elevate pg_restore -U postgres --no-owner -d NAME_new FILE`.
